Introduction to Lists and Arrays

Introduction

Lists and arrays are the starting point for almost everything else in this course. An array is an ordered sequence of elements stored under a single name, where each element is reached by a numeric index that normally begins at 0. That simple idea — position-based access — is what makes arrays fast for some tasks (reading or writing a known position) and slower for others (inserting or deleting in the middle, which may require shifting elements). A linked list stores the same kind of ordered data differently, chaining nodes together with references, which trades fast indexing for cheaper insertion and deletion.

In JavaScript, arrays are flexible: they can grow and shrink, hold mixed types, and come with built-in methods you will use constantly in this module. Before you can analyze or optimize array algorithms, you need comfort with the mechanics — length, bracket notation, zero-based indexing, and how out-of-range access behaves. That fluency is the foundation for the insertion, deletion, search, and traversal work that follows in Module 3.

As you watch, keep three questions in mind. First, what exactly does indexing cost compared with searching? Second, when would you prefer a linked structure over a contiguous array? Third, how does the ordered, indexed nature of an array shape the algorithms we can write on top of it? Jot down the trade-offs you hear; they reappear in the Big O discussions later in the module.

Insertion Operations

Introduction

Inserting an element into an array sounds trivial until you look at what the machine actually has to do. Because array elements occupy contiguous positions and are reached by index, adding a value anywhere other than the very end forces every element after that point to shift one slot to the right. That shifting is the whole story of insertion: it determines the algorithm you write, the edge cases you must handle, and the cost you pay.

In this topic we work through three cases. Insertion at the end is the cheap case, usually a constant-time operation (amortized, when a dynamic array occasionally has to grow and copy). Insertion at the beginning is the expensive case, because every existing element has to move. Insertion at an arbitrary position sits in between but is analyzed the same way in Big O terms. Alongside JavaScript's built-in methods such as push, unshift, and splice, you should be able to write the manual algorithm yourself: loop backward from the last element, copy each value one position forward, then place the new value in the opened slot.

As you watch the videos below, keep two questions in mind. First, how many elements move for this insertion, and how does that number depend on the insertion position and the array length? Second, what happens to capacity when the array is full? The examples are shown in C in two of the videos and in JavaScript in the third, but the underlying shifting behavior and the resulting O(n) worst case are the same in both languages.

Deletion Operations

Introduction

Deletion looks simple — "just remove the item" — but in an array it is rarely that simple. Because array elements live in contiguous positions, removing one from anywhere other than the end leaves a hole that must be repaired by shifting every following element back one slot. That shifting is the hidden cost behind most deletion operations, and it is the reason deleting from the end is cheap while deleting from the beginning or middle is not.

In this topic you will work through the main deletion scenarios: removing from the end, from the beginning, from an arbitrary middle index, and removing by value rather than by position. You will also contrast mutating approaches (which change the original array in place, such as pop, shift, and splice) with non-mutating approaches like filter, which leaves the original untouched and returns a new array containing only the elements you wanted to keep. Knowing which style you are using matters a great deal once arrays are shared across functions.

As you watch, keep three questions in mind. First, what physically happens to the remaining elements and to the length after a removal? Second, how many element moves does each operation require in the worst case — constant work, or work proportional to n? Third, does the method you are using modify the original array or return a new one? The videos below approach these questions from two angles: a low-level C view that makes the shifting and memory behavior visible, and a practical JavaScript walkthrough of the built-in methods you will actually write in this course.

Searching Algorithms

Introduction

Searching is one of the most common things we ask a program to do: given a collection of data, find whether a particular value is present and, if so, where. In this topic we look at two classic approaches. Linear search walks through a list one element at a time and compares each item to the target; it works on any array, sorted or not. Binary search repeatedly cuts a sorted array in half, discarding the portion that cannot contain the target, which makes it dramatically faster but adds the requirement that the data already be in order.

These algorithms matter in this course for two reasons. First, they are the simplest realistic setting for reasoning about Big O: linear search is O(n), binary search is O(log n), and you can see exactly why by counting comparisons. Second, they force you to think about trade-offs. Binary search is faster per lookup, but if the data is unsorted you must pay the cost of sorting first, so the "better" algorithm depends on the scenario.

As you watch the videos below, pay attention to three things: the preconditions each algorithm requires, the exact loop structure and index arithmetic (especially the low, high, and mid pointers in binary search, and how the boundaries are updated), and the comparison counts the presenters use to justify the running time. The videos use pseudocode and Python, so after watching, practice rewriting each algorithm in JavaScript using a while or for loop over an array, and test it on arrays where the target is first, last, in the middle, and absent entirely.

Traversal Techniques

Introduction

Traversal is the act of systematically visiting every element in a list or array so you can read, test, transform, or accumulate values. It is the foundation beneath almost every other array operation: searching, filtering, summing, copying, and rearranging all depend on some form of ordered visit to each element. In JavaScript you have several ways to express a traversal — a classic for loop with an index, a reverse loop counting down, a for...of loop over values, and higher-order methods such as forEach, map, filter, and reduce.

Each technique carries trade-offs. An index-based for loop gives you full control over the starting point, stopping condition, and step size, which is what you need for reverse traversal or for step-and-skip patterns like visiting every second element. A for...of loop is cleaner when you only need values and not positions. Higher-order methods are expressive and reduce boilerplate, but they hide the loop, so you still need to reason about what work is happening on each pass. Nested loops extend all of this to two-dimensional arrays, where an outer loop walks the rows and an inner loop walks the columns.

As you watch the videos below, pay attention to three things: which loop construct is used and why, how the index or iteration variable is controlled, and what the traversal costs in terms of how many elements are visited. Whenever a video shows a built-in method, try to picture the equivalent manual loop underneath it — being able to move between the two views is exactly the skill this module is building toward.

Time and Space Complexity Analysis

Introduction

Every operation you write on a list or array has a cost: the number of steps it takes as the data grows, and the extra memory it needs while running. Time and space complexity analysis gives you a vocabulary — Big O notation — for describing those costs in a way that is independent of your machine, your language, and the size of any particular test case. Instead of saying "this loop felt fast," you can say that traversal is O(n), that binary search on a sorted array is O(log n), or that inserting at the front of an array is O(n) because every later element must shift.

This matters in COP3530 because arrays and lists support the same operations with very different costs depending on where in the structure you work and whether the data is sorted. Knowing that access by index is O(1) but search by value is O(n), or that deletion from the end is cheap while deletion from the middle is not, is what lets you choose the right operation and the right structure for a problem rather than guessing.

As you watch the videos below, pay attention to three things: how a piece of code is translated into a count of operations, how lower-order terms and constants are dropped to produce the final Big O expression, and how the same operation (search, insert, delete, traverse) compares across different data structures. Try pausing and predicting the complexity of each example before the presenter reveals it — that habit is what the module assessments will ask you to do.
