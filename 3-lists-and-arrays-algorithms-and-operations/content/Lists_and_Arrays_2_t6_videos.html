Introduction

Every operation you write on a list or array has a cost: the number of steps it takes as the data grows, and the extra memory it needs while running. Time and space complexity analysis gives you a vocabulary — Big O notation — for describing those costs in a way that is independent of your machine, your language, and the size of any particular test case. Instead of saying "this loop felt fast," you can say that traversal is O(n), that binary search on a sorted array is O(log n), or that inserting at the front of an array is O(n) because every later element must shift.

This matters in COP3530 because arrays and lists support the same operations with very different costs depending on where in the structure you work and whether the data is sorted. Knowing that access by index is O(1) but search by value is O(n), or that deletion from the end is cheap while deletion from the middle is not, is what lets you choose the right operation and the right structure for a problem rather than guessing.

As you watch the videos below, pay attention to three things: how a piece of code is translated into a count of operations, how lower-order terms and constants are dropped to produce the final Big O expression, and how the same operation (search, insert, delete, traverse) compares across different data structures. Try pausing and predicting the complexity of each example before the presenter reveals it — that habit is what the module assessments will ask you to do.
