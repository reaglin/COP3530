Foundations of Computational Complexity

Introduction

Computational complexity theory is the study of how the resources an algorithm consumes — primarily time, but also space — grow as the size of its input grows. Rather than timing code on one machine with one data set, we count the operations that dominate the work and describe how that count scales. This abstraction lets us compare algorithms fairly, independent of hardware, programming language, or compiler.

In COP3530, this vocabulary is the foundation for everything that follows. Every data structure you meet this semester — arrays, linked lists, trees, hash tables, heaps, graphs — is judged by the cost of its operations, and those costs are stated in asymptotic terms. Before you can argue that one structure is the right choice for a problem, you need to be fluent in input size n, in best-, worst-, and average-case analysis, and in the notations Big O, Omega, and Theta.

As you watch the videos below, keep three questions in mind. First, what exactly is being counted, and what is being treated as the input size? Second, which case is under discussion — is the speaker describing a guarantee that always holds, or a happy accident on a lucky input? Third, which notation is appropriate for that claim: an upper bound (O), a lower bound (Omega), or a tight bound (Theta)? Being deliberate about these distinctions now will save you a great deal of confusion later.

Big O Notation Revisited

Introduction

Big O notation is the standard language for describing how an algorithm's running time or memory use grows as the input size grows. Rather than measuring seconds on a particular machine, Big O captures an upper bound on the rate of growth, which lets us compare algorithms in a way that stays meaningful across hardware, languages, and compilers. In this topic we revisit that idea carefully: what the notation actually asserts, the common growth classes you will see again and again (constant, logarithmic, linear, linearithmic, quadratic, exponential), and why constants and lower-order terms are dropped when only the dominant term matters at scale.

This matters throughout COP3530 because nearly every data structure decision you make is justified with a complexity argument. When you choose a hash table over a sorted array, or a balanced tree over a linked list, you are claiming something about growth rates. Reading Big O fluently also means recognizing patterns in code: a single loop over n elements, nested loops, a loop that halves the search space each iteration, or a recursive call structure each map to a predictable class.

As you watch, pay attention to three things. First, how each presenter defines Big O formally versus how they use it informally. Second, how they move from a piece of code to a growth expression and then simplify it. Third, the connection between Big O and worst-case analysis — Big O is often used for worst-case guarantees, but the notation itself and the case being analyzed are two separate choices, and keeping them distinct will save you confusion later in this module.

Best, Worst, and Average Case Analysis

Introduction

Every algorithm you write will behave differently depending on what you feed it. A linear search that finds its target in the first slot does almost no work; the same search looking for a value that isn't there must examine every element. Best-, worst-, and average-case analysis is the vocabulary we use to describe that variation precisely, instead of saying vaguely that an algorithm is "usually fast."

In this module the three cases sit alongside asymptotic notation. The two ideas are related but not the same: a case describes which input you are analyzing, while Big O, Omega, and Theta describe how you bound the resulting cost function. Keeping them separate is one of the most common stumbling blocks in COP3530, and it matters because exam questions, interview questions, and real design decisions all hinge on knowing which case a stated bound refers to.

As you watch, focus on three things. First, how does each speaker characterize the specific input that triggers each case — not just the formula, but the data arrangement that causes it? Second, how is the average case actually computed, since it requires assumptions about input distribution rather than a single example? Third, note which algorithms have three different answers (linear search, bubble sort, quicksort) and which collapse to the same bound in all cases (selection sort, merge sort), and ask yourself why.

Omega and Theta Notations

Introduction

So far in this module you have used Big O to describe how an algorithm's running time grows in the worst case — an upper bound on the work required. But an upper bound alone tells an incomplete story. If someone says an algorithm is O(n^2), that statement is technically true even for an algorithm that always runs in constant time, because Big O only promises the growth is no worse than the stated function. To describe performance precisely, we need two more tools: Omega notation for lower bounds and Theta notation for tight bounds.

Omega (Ω) says the running time grows at least as fast as some function — it establishes a floor. Theta (Θ) applies when the upper and lower bounds match, pinning the growth rate from both directions and giving the most informative single description of an algorithm's behavior. Together, O, Ω, and Θ form a vocabulary that lets you state exactly what you are claiming: a guarantee you will never exceed, a limit you cannot beat, or an exact characterization of growth.

While watching these videos, pay close attention to the formal definitions — each notation is defined by an inequality involving constants c and n0, and the differences between them come down to the direction of that inequality. Also notice how the speakers connect the formal definitions back to familiar algorithms. Ask yourself for each course algorithm we have studied, such as linear search, binary search, bubble sort, and merge sort, whether its best case and worst case match. When they match, Theta applies; when they differ, you must be careful to say which case you are describing.

Comparing Asymptotic Notations

Introduction

When we analyze an algorithm, we rarely want a single number — we want a statement about how the running time behaves as the input grows. Big O, Omega, and Theta are the three standard tools for making that statement precise. Big O gives an upper bound (the work grows no faster than this), Omega gives a lower bound (the work grows at least this fast), and Theta gives a tight bound (the growth is pinned between the two, up to constant factors).

In this course these notations are not interchangeable vocabulary; they encode different claims. Saying linear search is O(n) is a guarantee about the worst case, while saying any comparison sort is Omega(n log n) is a claim about an inherent limit, and saying merge sort is Theta(n log n) says both bounds coincide. Choosing the wrong notation can make a correct analysis say the wrong thing, which is why this topic focuses on the relationships among the three and on when each is the right reporting choice.

As you watch the videos below, pay attention to three things: the formal definitions with their constants c and n0, the picture of a function being sandwiched between scaled versions of another, and the logical relationship that f is Theta(g) exactly when f is both O(g) and Omega(g). Also note how speakers distinguish best/worst/average case from upper/lower/tight bound — these two ideas are related but are not the same thing, and conflating them is the most common error students make here.

Complexity Analysis of Known Algorithms

Introduction

So far in this course you have learned the vocabulary of asymptotic analysis — Big O, Omega, and Theta — and the mechanics of counting operations. This topic puts that vocabulary to work on algorithms you already know how to code: linear search, binary search, bubble sort, selection sort, and merge sort. The goal is not to memorize a table of complexities but to be able to reconstruct each result from the structure of the algorithm itself.

That skill matters because the same handful of structural patterns reappear constantly. A single pass over n elements gives you O(n); a loop nested inside another loop over the same data gives you O(n^2); repeatedly halving a search space gives you O(log n); and splitting a problem in half and merging the results gives you O(n log n). Once you can recognize these patterns, you can analyze unfamiliar code without memorizing anything new.

As you watch the videos below, pay attention to three things: which operation is being counted as the dominant one, how the count changes between the best, average, and worst case, and why a particular notation is chosen to report the result. Notice especially that an algorithm can have different best- and worst-case behavior — optimized bubble sort is the classic example — and that reporting only Big O hides that distinction. Try pausing each video and deriving the bound yourself before the presenter states it.

Practical Implications of Complexity

Introduction

Up to this point in the module you have been learning how to analyze algorithms: identifying dominant operations, dropping lower-order terms, and expressing growth rates with asymptotic notation. This topic asks the natural follow-up question: so what? Complexity analysis earns its place in software engineering because it lets you predict how a program will behave at scales you have not tested yet, and because it gives you a shared vocabulary for defending design decisions to teammates, managers, and clients.

Practical implications show up in several recurring decisions. Which sorting routine or search strategy should you reach for given the size and shape of your data? Where should you spend your limited optimization effort — on the O(n^2) nested loop or on the constant-factor tweak that feels slow but barely matters? When is it worth spending extra memory (a hash table, a cache, a precomputed index) to buy down running time, and when does that trade go the wrong way? And how do you explain "this will be fine for a thousand records but not for ten million" to someone who does not read asymptotic notation?

The three videos below review the analytical tools and then apply them to concrete algorithm comparisons. While watching, keep a practical lens: note how each algorithm's time and space costs would influence a real selection decision, pay attention to where best-case and worst-case behavior diverge (that gap is exactly what you must communicate to stakeholders), and watch for the common code patterns that quietly push an implementation into a higher growth class.
