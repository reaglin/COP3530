Foundations of Data Structures in Real-World Systems

Introduction

So far in COP3530 you have studied hash tables, trees, and graphs mostly as isolated topics: how each one is built, how it performs, and how to implement it. This topic shifts the perspective. Real systems rarely use a single structure in isolation — they layer and combine them. A database might use a hash index for point lookups, a B-tree for range queries, and a log-structured file for durable writes, all inside one engine. A blockchain combines a linked list, cryptographic hashing, and a Merkle tree. A social platform stores relationships as a graph while using hash tables to find a user's record in constant time.

The subtopics here build that layered view. Hash tables are the lookup foundation: constant-average-time access keyed by a value you compute rather than search for. Trees are hierarchical organizers: they keep data sorted, support ranges and prefixes, and summarize subtrees. Graphs model relationships that have no natural hierarchy — friendships, transactions, routes, dependencies. Composition is where these meet, and the conceptual framework is the habit of asking, for any system: what operations must be fast, what structure makes them fast, and what does that choice cost?

As you watch, resist the urge to just collect names of structures. For each one mentioned, ask three questions: what operation is it optimizing, what does it give up in exchange, and what would break if you swapped in a different structure? Jot down any case where two structures are used together — those composition examples are exactly what you will be asked to analyze and design later in this module.

Blockchain Architecture and Data Structures

Introduction

A blockchain is, at its core, a data structures problem. Strip away the economics and the hype and what remains is a singly linked list whose "pointers" are cryptographic hash digests rather than memory addresses, with each node (a block) carrying a tree of transactions summarized by a Merkle root. The structural choices are what produce the properties people care about: because every block header contains the hash of the previous header, altering any historical transaction changes that block's hash, which invalidates every link downstream. Immutability here is not a policy or a promise — it is a consequence of how the structure is wired together.

In this course, blockchain serves as a case study in composition. You have already studied linked lists, hash functions and hash tables, and binary trees in isolation; here you see them stacked so that each one does a specific job. Hashing provides a fixed-size fingerprint and collision resistance. The Merkle tree lets a verifier confirm that a single transaction belongs to a block using only O(log n) sibling hashes instead of downloading the whole block. The block header bundles the metadata (previous hash, Merkle root, timestamp, nonce, difficulty) that makes validation cheap. Distribution and consensus then decide which chain the network accepts when two valid chains exist.

As you watch the videos below, keep a running list of questions: Which structure is being used, what operation does it make fast, and what does it cost? Where does a hash act as an identifier versus as an integrity check? How does a Merkle proof differ from re-hashing an entire block? Note that these videos come from industry and educational channels rather than an algorithms course, so you may need to translate their vocabulary back into the data structures terms we use in lecture.

Digital Currency Systems

Introduction

Digital currency systems are a useful case study for this course because almost every component of a cryptocurrency is, underneath the marketing language, a familiar data structure doing a specific job. A wallet is essentially a key-value store mapping keys and addresses to spendable funds. Pending transactions sit in a mempool, a priority-ordered holding area that nodes draw from. Confirmed transactions are summarized by a Merkle tree so that membership can be verified with a short proof instead of a full scan, and blocks are chained together much like a linked list in which each node stores a hash pointer to its predecessor.

Two accounting models dominate. In the UTXO (unspent transaction output) model used by Bitcoin, a wallet balance is not a stored number at all but the sum of a set of discrete unspent outputs, each of which must be consumed whole and replaced by new outputs. In the account model used by Ethereum, balances are stored directly in a mutable key-value map. The choice between these shapes everything downstream: storage size, lookup cost, parallelism, privacy, and how easily the system scales.

As you watch the videos below, keep translating the vocabulary back into course terms. When you hear "UTXO set," ask what structure holds it and what the cost of a lookup or update is. When you hear "hash," ask what properties make it suitable for linking blocks and for building Merkle trees. When you hear about fees and consolidation, ask what trade-off is being made between storage footprint, computation, and user privacy — that habit of naming the trade-off is exactly what the module assessments will ask for.

Graphs and Social Network Applications

Introduction

Social networks are, at their core, graphs: people (or accounts, pages, wallets) are vertices, and relationships (friendship, following, messaging, transactions) are edges. Once you model a platform this way, questions that sound social become questions about graph structure — How many hops separate two users? Which accounts sit at the center of a cluster? Which groups of users are densely connected to each other but sparsely connected to everyone else? How fast would a post spread if it started here?

In this module you have been looking at how real systems compose data structures to meet concrete requirements, and graphs are the structure that carries relationship and influence. Two representation choices dominate practice: the adjacency matrix, which gives constant-time edge lookup at the cost of space proportional to the square of the vertex count, and the adjacency list, which is far more compact for the sparse graphs that real social networks actually are. On top of whichever representation you choose, the two workhorse traversals — breadth-first search and depth-first search — power features such as degrees-of-separation and "people you may know" (BFS, which explores level by level) and connected-component or community discovery (DFS, which dives deep along a path before backtracking).

The videos below focus on those traversals, since mastering BFS and DFS mechanics is what makes the application-level topics (centrality, information flow, platform design) tractable. While you watch, pay attention to three things: the auxiliary structure each algorithm uses (queue for BFS, stack or recursion for DFS), how the visited set prevents infinite looping in cyclic graphs, and the order in which vertices are discovered. Then mentally re-map each example graph onto a friend network and ask what the traversal output would mean in that setting.

Combining Data Structures in Complex Systems

Introduction

Up to this point in the course you have studied data structures largely one at a time: a linked list here, a hash table there, a tree or graph in isolation. Real systems almost never work that way. A blockchain node, a payment network, or a social platform stitches several structures together — hash tables for fast lookup, linked structures for ordering and history, trees for verification, graphs for relationships — and layers them so that each structure handles the operation it is best suited for.

This topic asks you to think like a system designer rather than a single-structure implementer. Blockchain is our primary case study: hash-linked blocks, cryptographic digests, and Merkle trees combine to give immutability and efficient transaction verification, while hash tables and indexes make wallet balances and transaction lookups practical. Social and transactional networks give us a second case study, where the choice between adjacency lists and adjacency matrices, and between BFS and DFS traversal, directly changes storage cost and feature performance.

The three videos below come from ByteByteGo, a system design channel, and they frame the same question from an industry perspective: which structures, algorithms, and storage engines do large systems actually combine, and why. As you watch, keep a running list of the data structures mentioned, note the trade-off that justifies each one (time versus space, read speed versus write cost, simplicity versus scalability), and ask how you would describe that same decision using the formal cost analysis you have learned in this course.
