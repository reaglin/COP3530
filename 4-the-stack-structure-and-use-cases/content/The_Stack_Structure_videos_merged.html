Introduction to the Stack Data Structure

Introduction

A stack is one of the simplest and most widely used data structures in computer science. It stores a collection of items but deliberately restricts how you interact with them: you may only add or remove at one end, called the top. That single restriction produces the Last-In, First-Out (LIFO) ordering that gives stacks their character — the most recently added item is always the first one to leave.

In this module we build toward implementing a Stack class ourselves, so it matters that you first understand the stack conceptually, independent of any code. That is the idea behind treating a stack as an Abstract Data Type (ADT): we specify the operations it must support — push, pop, peek, isEmpty, size — and the rules governing their behavior, and only afterward decide whether an array, a linked list, or something else will hold the data underneath.

As you watch, pay attention to three things. First, how each video describes what happens to the top of the stack during push and pop. Second, the distinction between the interface (what operations exist and what they promise) and the implementation (how they are carried out). Third, any mention of where stacks appear in real systems — function call stacks, undo features, backtracking — since those use cases return later in the module.

The LIFO Principle

Introduction

A stack is one of the simplest data structures you will study in this course, and almost all of its behavior follows from a single rule: Last In, First Out, or LIFO. Whatever element was added most recently is the only one you are allowed to remove next, and the only one you are allowed to inspect. That restriction is not a limitation to work around — it is the entire point, because it makes the structure predictable, fast, and a perfect match for problems that unwind in reverse order.

In this topic we define LIFO precisely, ground it in a familiar physical analogy (a stack of plates or trays), and contrast it with other ordering principles you already know — the First In, First Out rule of a queue, and the index-based random access of an array. We then look at the two operations that enforce LIFO, push and pop, and at the idea of the 'top': a single reference or index that marks where the next push lands and where the next pop comes from. Understanding the top is what makes later discussions of constant-time operations and underlying containers make sense.

As you watch the videos below, keep three questions in mind. First, where exactly is the top, and how does it move during a push versus a pop? Second, what happens when you pop an empty stack or push onto a full one — how is that condition detected? Third, what kinds of problems would become harder if you were allowed to reach into the middle of the stack? That last question is the bridge to Module 4's later topics on undo features, call stacks, and expression evaluation.

Internal Implementation of a Stack

Introduction

A stack is simple to describe — last in, first out — but to use it well you need to know what is happening underneath. Internally, a stack is just a container (commonly an array, sometimes a linked list) plus a single marker, the top, that tells you where the next item goes and which item comes off next. Every core operation is defined in terms of that marker: push writes at the top and advances it, pop reads at the top and retracts it, peek reads without changing it, and size is derived from it.

This topic matters in COP3530 because you will build a Stack class in JavaScript rather than only use one. Writing push and pop yourself forces you to confront the details that are easy to gloss over: what the top should be when the stack is empty, what happens when you pop an empty stack (underflow) or push onto a full fixed-size array (overflow), and how to keep the internal container private so callers cannot bypass LIFO ordering. The same reasoning explains why push and pop are O(1) time while the stack as a whole is O(n) space.

As you watch, track three things in every example: where the top marker sits before and after each operation, the exact order of the steps inside push and pop (check the boundary first, then move the pointer and the data), and which parts of the implementation would change if you swapped an array for a linked list. The videos below use array-based stacks in C-style pseudocode and code; your job is to carry the mechanics over to a JavaScript class.

Introduction

A stack is one of the simplest data structures you will build, and that simplicity is exactly why it is worth building yourself. In this topic you will write a Stack class from scratch in JavaScript: a constructor that sets up the internal storage (commonly an array), a push method that adds an item to the top, a pop method that removes and returns the top item, and a peek method that lets you look at the top without removing it. You will round the class out with isEmpty and size helpers and a print or toString method so you can inspect the contents while debugging, then test everything with a sequence of operations that proves the Last-In, First-Out ordering actually holds.

This matters because almost everything later in the course leans on stacks. Expression parsing, backtracking, recursion and the JavaScript call stack itself all depend on the same handful of constant-time operations you are about to write. Once you have implemented the class, the behavior of those higher-level algorithms becomes much easier to reason about, because you know exactly what happens on each push and pop.

Expression Evaluation Using Stacks

Introduction

Expressions like 3 + 4 * (2 - 1) are easy for people to read, but a computer cannot simply scan them left to right and get the right answer. Operators have different precedence levels, parentheses override those levels, and some operators associate left to right while others associate right to left. The stack solves this problem elegantly: whenever you encounter something whose handling must be postponed — an open parenthesis, an operator of lower precedence, an operand waiting for its operator — you push it and come back to it later, in exactly the reverse order you set it aside. That Last-In, First-Out behavior is what makes stacks the natural tool for parsing.

In this topic you will work through the chain of ideas that compilers and calculators actually use: checking that parentheses and brackets are balanced, understanding the three notations (infix, prefix, postfix), converting infix to postfix with the Shunting-Yard algorithm, and then evaluating a postfix expression with a single stack and a single left-to-right pass. The payoff is that postfix needs no parentheses and no precedence rules at evaluation time — all of that complexity is resolved during conversion.

As you watch the videos below, trace each example by hand with pencil and paper. Keep a column for the stack contents and a column for the output at every step, and pay close attention to the rules that govern when an operator is pushed versus when it forces pops: comparing precedence of the incoming operator against the top of the stack, handling equal precedence according to associativity, and treating the open parenthesis as a barrier that only a matching close parenthesis can remove.

Undo Mechanisms and Other Real-World Use Cases

Introduction

Up to this point you have studied the stack as an abstract structure: a container with push, pop, and peek, governed by a Last-In, First-Out rule. This topic asks a different question — where does that rule actually show up in the software you use every day? The answer is: almost everywhere. Pressing Ctrl+Z in a text editor, clicking the back button in a browser, watching a function return control to its caller, checking whether parentheses balance in an expression, or exploring a maze until you hit a dead end and retreat — all of these are LIFO behavior wearing different costumes.

The common thread is reversal. Whenever a system needs to undo the most recent thing first, or return to the most recently suspended state, a stack is the natural fit. An undo feature pushes each action onto a stack and pops them off in reverse order. Browser history pushes each visited page, and the back button pops. The call stack pushes a frame for every function invocation and pops it when the function returns, which is also why infinite recursion produces a stack overflow. Expression parsers push operators and operands until they can be resolved, and backtracking algorithms push partial solutions so they can retreat when a path fails.

As you watch the video below, keep a mental checklist: What is being pushed? When is it pushed? What triggers the pop? If you can answer those three questions for any feature, you can decide whether a stack is the right tool. Pay particular attention to the call stack, since it is the example that is both the most invisible to everyday users and the most important for you as a programmer — it explains recursion, return addresses, local variable lifetimes, and a whole category of runtime errors.
