Introduction to Hash Tables

Introduction

A hash table is a data structure that stores key-value pairs and, in the average case, lets you insert, look up, and remove an entry in constant time. Instead of scanning a list to find a key, a hash table runs the key through a hash function that produces a number, and that number is converted into an index in an underlying array. The array does the actual storing; the hash function is what tells you where to look.

This topic matters because hash tables sit underneath many of the tools you already use — dictionaries, maps, sets, caches, symbol tables, database indexes — and because the rest of this module builds directly on it. Before you can reason about collisions, load factors, or chaining versus open addressing, you need a clear mental picture of the key-to-index mapping and of the array that the mapping points into.

While watching these videos, focus on three things. First, what exactly the hash function takes in and what it produces. Second, how that output becomes a valid array index (watch for the modulo step). Third, the moment where two different keys land on the same index — that is a collision, and noticing where it comes from now will make the collision-resolution material later in the module much easier.

Internal Array-Based Design

Introduction

A hash table is not a new kind of memory — it is a clever way of using an ordinary array. The array gives you constant-time access to any slot once you know its index, and the hash function is the piece that turns a key (a string, a number, an object) into one of those indices. Understanding this layering is the key to the whole module: everything else, including collisions and load factor, follows from the fact that we are squeezing a large space of possible keys into a fixed, finite set of array positions.

In this topic we focus on the mechanics of that mapping. A hash function takes a key, computes a numeric hash code, and then reduces it into the valid index range (commonly with the modulo operator against the table size). Because the result is computed rather than searched for, storage and retrieval can be O(1) on average — but only if the function is fast to compute and spreads keys reasonably evenly. The function must also be deterministic: the same key must always produce the same index, or you will store a value in one slot and look for it in another.

While watching, pay attention to three things. First, how each presenter describes the step from key to hash code to array index. Second, what assumptions they make about table size and the modulo step. Third, the moment collisions are introduced — notice that collisions are an unavoidable consequence of the array-based design, not a bug in it. That observation sets up the collision resolution material later in this module.

Hash Function Design and Properties

Introduction

A hash function is the engine of a hash table: it takes a key — a string, an integer, or any other value — and converts it into an index in an underlying array. Everything a hash table promises, including near constant-time insertion, lookup, and deletion, depends on how well that conversion is done. In this topic we look closely at the three properties that define a good hash function: determinism (the same key must always produce the same index), uniform distribution (keys should spread evenly across the table rather than piling into a few slots), and computational speed (hashing must be cheap, since it happens on every operation).

We also examine the mechanics behind common hash functions. For integers, the division method using the modulo operation is the usual starting point; for strings, techniques typically combine character codes with a multiplier (polynomial rolling hashes) before reducing the result modulo the table size. The modulo operation is what guarantees that any hash value lands inside the array bounds, and the choice of table size — prime versus power of two — directly affects how evenly values are distributed.

Finally, we consider what goes wrong when a hash function is poorly designed. Clustering, long collision chains, and lookups that degrade from O(1) toward O(n) are all symptoms of non-uniform hashing. As you watch the videos below, pay attention to how each one computes an index from a key, where collisions appear, and how the table size influences the result — those observations connect directly to the collision resolution strategies covered next in this module.

Collision Resolution: Chaining

Introduction

A hash function turns a key into an array index, but no matter how good that function is, two different keys will eventually land on the same index. That event is called a collision, and every usable hash table needs a plan for it. Chaining is the most common plan: instead of storing a single key-value pair in each bucket, each bucket holds a small container — usually a linked list — and every pair that hashes to that index is appended to the chain.

This topic walks through what that means in practice. Insertion means finding the bucket and adding a node to its chain; searching means hashing to the bucket and then walking the chain comparing keys; deletion means unlinking a node from a chain, which is noticeably simpler than deletion under open addressing, where removing an element can break probe sequences. The key performance idea is the load factor (number of stored entries divided by number of buckets): as it rises, average chain length rises with it, and lookup drifts from O(1) toward O(n) in the worst case where every key collides.

As you watch, keep three questions in mind. First, what exactly is stored in the array — values, or pointers to list nodes? Second, why must you still compare keys after reaching the right bucket? Third, how does chaining compare to open addressing on memory overhead, tolerance for high load factors, and ease of deletion? You will implement chaining yourself later in the module, so pay attention to the structure of the code as well as the diagrams.

Collision Resolution: Open Addressing

Introduction

When two keys hash to the same index, a hash table needs a plan. Open addressing is one such plan: instead of storing colliding items in a separate structure like a linked list, every element lives directly in the table array, and a collision sends the insertion routine looking for another empty slot according to a fixed, repeatable rule. That rule is called the probe sequence, and the three classic versions you will meet here are linear probing (try the next slot, then the next), quadratic probing (step away by growing squared offsets), and double hashing (let a second hash function determine the step size).

This matters in COP3530 because open addressing is the main alternative to separate chaining, and the comparison is a recurring exam and interview topic. Open addressing avoids pointer overhead and keeps data contiguous in memory, but it imposes constraints chaining does not: the load factor can never exceed 1, performance degrades sharply as the table fills, and deletion cannot simply blank out a slot without breaking the probe sequences that pass through it — hence tombstone or lazy-deletion markers.

As you watch the videos below, keep a pencil handy and build the table yourself alongside the instructor. Watch specifically for three things: the exact formula used to compute each successive probe, how the search operation must follow the same sequence that insertion used, and where clustering appears — primary clustering in linear probing, secondary clustering in quadratic probing — and how each later technique tries to reduce it.

Performance Analysis of Hash Tables

Introduction

Hash tables are often described as offering "constant time" lookup, insertion, and deletion, but that claim comes with conditions. The O(1) average case depends on a hash function that spreads keys evenly, a load factor that is kept under control, and a collision resolution strategy that does not degenerate. When any of those assumptions breaks down, performance slides toward O(n) — the same cost as scanning a plain array.

In this topic you will work through what actually drives hash table performance: the load factor (the ratio of stored entries to table slots), how often collisions occur, and how chaining and open addressing each respond as the table fills. You will also look at the space side of the trade-off — the extra pointers chaining requires, the empty slots open addressing needs to stay fast, and the amortized cost of resizing and rehashing when the table grows.

As you watch the videos below, keep three questions in mind. First, what operation is being performed at each step, and how many probes or list traversals does it take? Second, how would that count change if the table were nearly full versus mostly empty? Third, what input would force the worst case — and why does that matter for real systems that accept untrusted keys?

Implementing a Hash Table in JavaScript

Introduction

A hash table turns a key into an array index with a hash function, then stores a key-value pair at that slot. Because different keys can hash to the same index, every real implementation needs a collision resolution strategy. In this topic you will build the structure yourself in JavaScript: a HashTable class holding an array of buckets, a hash function that converts keys into valid indices, and set, get, remove, and keys methods that use separate chaining — each bucket holding a list of entries rather than a single value.

This hands-on work matters because it makes the theory concrete. Once you have written the loop that walks a bucket's chain looking for a matching key, the claim that lookup is O(1) on average but O(n) in the worst case stops being abstract: the length of that chain is exactly what determines the cost. Writing the remove method also exposes why deletion is simpler under chaining than under open addressing.
