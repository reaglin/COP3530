Introduction to Hash Compression

Introduction

Hashing lets us store and retrieve data in roughly constant time by computing where an item belongs instead of searching for it. But a hash function usually produces a value from a very large space — think of every possible string, every possible integer, every possible student ID — while the table we actually allocate has only a modest number of slots. Hash compression is the step that bridges that gap: it maps a large, unbounded set of hash codes or keys onto the bounded range of valid array indices, typically 0 through tableSize - 1.

This introductory topic sets up the vocabulary you will use for the rest of the module: key, hash code, compression function, index, bucket, collision, and load factor. It also frames the central tension you will return to repeatedly — compressing many keys into few slots guarantees that some keys will collide, so the goal is not to avoid collisions entirely but to spread keys as uniformly as possible while keeping the computation cheap.

As you watch the videos below, focus on three things. First, notice exactly where in the pipeline the key is converted into an index — that step is the compression we are naming. Second, pay attention to how table size enters the picture, since the size of the index range is a design choice with real consequences. Third, listen for how each presenter describes collisions, because that language will anchor the later subtopics on distribution uniformity and effective hash function properties.

Modular Arithmetic as a Compression Strategy

Introduction

Hashing turns a key into an index, but the raw output of a hash function is almost never in the range your table actually occupies. Compression is the step that maps that arbitrary integer into a valid slot number between 0 and M-1, and the most common compression strategy is the modulo operation: index = hash(key) % M. It is cheap, easy to reason about, and — when M is chosen well — spreads keys fairly evenly across the table.

The interesting part is the "chosen well." Because modulo keeps only the remainder, any structure in your keys can survive compression and pile up in a few buckets. Table sizes that are powers of two throw away all but the low-order bits; table sizes that share factors with patterns in your data create regular collisions. Prime table sizes are the standard defense, and load factor (n/M) tells you when the table itself needs to grow. This topic also asks you to recognize the failure cases of plain modular compression, which motivates alternatives such as multiplicative and universal hashing.

As you watch, keep three questions in mind: where exactly in the pipeline does compression happen, what assumptions about the key distribution is a given method making, and what happens to lookup cost as the load factor climbs. The videos below move from a plain-language introduction to hashing, to a concrete look at how hash tables use the modulo step, to a more formal alternative that explains why modulo alone is not always enough.

Folding and Other Compression Techniques

Introduction

Hashing turns a key of almost any size into an index that fits inside a bounded table. The compression step is where that shrinking actually happens, and this topic surveys the family of techniques that go beyond simple modular arithmetic. Folding methods split a key into equal-sized segments — digits, bytes, or bit groups — and combine those segments, usually by addition, so that every part of the key influences the final index. Shift folding adds the pieces as they are; boundary folding reverses alternating pieces before adding, which helps when neighboring keys differ only in position-sensitive ways.

Two other classic strategies round out the picture. Digit extraction selects only certain positions from the key, discarding digits that carry little variation (such as a shared prefix in student IDs). The mid-square method squares the key and extracts the middle digits, relying on the fact that the middle of a product depends on nearly all digits of the original. Each approach trades off differently among speed, distribution quality, and how much you need to know about your key population in advance.

The videos below build the surrounding context you need to evaluate these techniques. As you watch, keep three questions in mind: does every bit or digit of the key influence the output, how cheap is the operation to compute, and what assumptions about the key distribution does the method quietly make? Those same three questions are how you will compare folding, digit extraction, mid-square, and multiplicative or modular hashing later in the module.

Distribution Properties of Hash Functions

Introduction

A hash function's job is not just to turn a key into an index — it is to spread keys across the table so that no single slot becomes a bottleneck. The ideal we measure against is a uniform distribution: every index in the range is equally likely for an arbitrary key, independent of what other keys hashed to. Real compression techniques fall short of this ideal in predictable ways, and the result is clustering, where keys pile up in a few regions of the table while others sit empty.

This topic connects the mechanics you learned earlier (modular arithmetic, folding, digit extraction, mid-square) to their consequences for performance. Load factor — the ratio of stored items to table slots — determines how much room the table has to absorb collisions, and the choice of table size interacts strongly with the compression step (for example, a modulus that shares factors with patterns in your keys will collapse many keys onto few indices). Measuring distribution quality means looking at slot occupancy counts, longest chain length, and average probe or comparison count rather than just checking that the function "works."

As you watch, keep three questions in mind. First, where in each example does a collision actually come from — the key values, the compression step, or the table size? Second, how does the cost of a lookup change as more keys land in the same slot? Third, what property of the hash function would have prevented that pileup? The videos below move from the basic mechanics of hashing, to what happens when keys collide, to a more formal notion of a hash function with provably good distribution behavior.

Comparing and Selecting Compression Methods

Introduction

Once you know several ways to compress a hash code into a table index — modular arithmetic, mid-square, digit extraction, and the folding methods — the next question is practical: which one should you actually use? This topic gives you a framework for answering that. The three criteria we weigh are compression efficiency (how much arithmetic work each key costs), distribution uniformity (how evenly keys spread across the table and therefore how often collisions occur), and implementation complexity (how much code, tuning, and maintenance the method demands).

None of these criteria wins outright. A fast method that clusters keys may produce more collisions than its speed savings justify, while a method that scatters keys beautifully may be too fiddly to justify in a simple lookup table. The right choice depends on the use case: key patterns, table size, expected load factor, whether the table resizes, and whether the system is distributed. Good selection is also iterative — you pick a candidate, test it against realistic key data, measure collision counts and bucket occupancy, and revise.

The videos below approach this from three angles. The first reviews hashing fundamentals and names several compression methods, giving you the vocabulary to compare them. The second shows what happens downstream when compression distributes keys poorly, which is how uniformity gets measured in practice. The third moves to a real system-design use case where an ordinary modulo compression fails and a different strategy is required. As you watch, keep asking: what does this method cost, how evenly does it spread keys, and what situation would make it the right or wrong pick?
