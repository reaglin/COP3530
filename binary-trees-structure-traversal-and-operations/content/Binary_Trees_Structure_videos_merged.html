Introduction to Binary Trees

Introduction

A binary tree is a hierarchical data structure built from nodes connected by edges, where every node has at most two children, conventionally called the left child and the right child. Unlike arrays and linked lists, which arrange data in a single line, trees branch — and that branching is what makes them so useful for organizing data that will later be searched, sorted, or traversed. Before you can insert into or search a binary search tree, you need fluency with the vocabulary: node, edge, root, leaf, parent, child, sibling, subtree, depth, and height.

This topic is the foundation for everything else in the module. The root node is the single entry point with no parent; leaf nodes are the endpoints with no children; every other node sits in a parent-child relationship that defines the shape of the structure. The "binary constraint" — at most two children per node — is the structural rule that separates binary trees from general trees, and it is what makes traversal and search algorithms predictable enough to analyze.

As you watch, focus on the terminology and on the pictures. Try to redraw each example tree yourself and label the root, the leaves, and the edges. Ask yourself for every diagram: how many children does each node have, which nodes are parents of which, and would this structure still qualify as a binary tree if one more child were added? Pay attention also to how speakers distinguish a general binary tree from the more constrained variants (full, complete, perfect, and binary search trees) that come later in the module.

Node Structure and Tree Anatomy

Introduction

Before you can traverse, search, or rebalance a tree, you need a precise vocabulary for its parts. A binary tree is built from nodes, and each node is a small, self-contained unit: a field holding the data (often called the key or value) and two reference fields pointing to a left child and a right child. When either reference is null, that side of the node is empty — and a node with two null references is a leaf. Everything else about tree structure follows from how these nodes are linked together.

From those links come the relationships and measurements you will use all semester. One node is designated the root (the only node with no parent); every other node has exactly one parent and up to two children. The depth of a node is the number of edges from the root down to it, the height of a node is the number of edges on the longest downward path to a leaf, and the height of the tree is the height of its root. Any node, taken together with everything beneath it, forms a subtree — which is why so many tree algorithms are naturally recursive. Nodes sharing the same depth form a level, and a tree is considered balanced when the left and right subtrees of every node have heights that differ by at most a small constant.

These ideas are not just terminology. Tree height directly determines how long a search or insertion takes, so the difference between a balanced tree and a degenerate, list-like tree is the difference between logarithmic and linear performance. As you watch the videos below, pay attention to three things: how height and depth are defined (some sources count edges, others count nodes, so note which convention is used), how a recursive height computation mirrors the subtree structure, and what makes the minimum and maximum possible heights of an n-node tree so far apart.

Binary Search Trees (BST) Concepts

Introduction

A binary search tree (BST) is a binary tree with one extra rule attached to it: for every node, all values in its left subtree are smaller than the node's value, and all values in its right subtree are larger. That single ordering property is what separates a BST from a general binary tree, and it is the reason a BST can do useful work that an unordered tree cannot. Each node still looks familiar — a data field plus left and right child pointers — but the arrangement of those nodes now carries meaning.

The payoff is search. Because you can compare a target value to the current node and discard an entire subtree in one step, searching a BST resembles binary search on a sorted array: you halve the remaining possibilities at each level rather than inspecting every node. That gives O(log n) behavior when the tree is reasonably balanced. The catch, which this topic also introduces, is that performance depends on height, not on node count alone — inserting already-sorted data produces a long, skinny tree that degrades to O(n), essentially a linked list wearing a tree costume.

As you watch these videos, keep three questions in mind. First, how is the ordering property stated — does it apply only to immediate children, or to entire subtrees? (The subtree version is the correct one.) Second, how does each presenter walk a search path, and can you predict the comparisons before they do? Third, what does the tree look like in the worst case, and what does that do to the running time? You will use these ideas immediately when you move on to insertion, deletion, and your own implementation.

Insertion and Search Operations

Introduction

A binary search tree (BST) is more than a tree of nodes — it is a tree that obeys an ordering property: for every node, all keys in its left subtree are smaller, and all keys in its right subtree are larger. Insertion and search are the two operations that both depend on and preserve this property. When you insert, you start at the root and repeatedly move left or right by comparing the new key to the current node, until you reach an empty spot where the new node belongs. Search follows the exact same path logic, except it stops when it finds a match or runs out of nodes to visit.

This matters in COP3530 because the BST is the first structure where the shape of the data determines performance. Each comparison discards roughly half of the remaining tree when the tree is reasonably balanced, giving O(log n) behavior for both insert and search. But insert values in sorted order and the tree degenerates into a chain — a linked list in disguise — and performance collapses to O(n). Understanding why requires connecting the insertion logic to the resulting tree height, not just memorizing two complexity classes.

As you watch, keep three things in view. First, track the comparison at each node and notice that insertion and search share identical traversal logic. Second, watch how the code expresses this — iteratively with a while loop and a trailing parent pointer, or recursively by returning subtrees. Third, pay attention to the examples used: ask yourself what the tree would look like if the same keys had arrived in a different order, and what that does to the number of comparisons.

Deletion Operations

Introduction

Deletion is the trickiest of the three core binary search tree operations. Insertion and search only ever move downward along a single path, but deletion removes a node that other nodes depend on, so the tree must be repaired afterward. The standard approach breaks the problem into three cases based on how many children the target node has: zero (a leaf), one, or two.

The first two cases are straightforward — a leaf can simply be unlinked from its parent, and a node with a single child can be replaced by that child. The third case requires more care: a node with two children cannot simply be removed, so its value is overwritten with either its in-order successor (the smallest value in the right subtree) or its in-order predecessor (the largest value in the left subtree), and then that replacement node is deleted recursively. Either choice preserves the BST ordering property, which is the invariant everything else in this module depends on.

As you watch, pay attention to three things: how each video identifies which case applies, how the parent pointer or returned subtree reference is reattached after removal, and how the successor or predecessor is located. Try pausing and predicting the resulting tree before the presenter reveals it — tracing deletions by hand is the fastest way to internalize the logic you will later implement in code.

Tree Traversal Strategies

Introduction

Traversal is how we systematically visit every node in a binary tree exactly once. Because a tree has no single linear order built into it, we have to choose a rule for the order in which we touch the root and its two subtrees. The three classic depth-first rules are in-order (left, root, right), pre-order (root, left, right), and post-order (left, right, root). Each is a tiny variation on the same recursive idea, but each produces a very different output sequence.

Those differences matter in practice. In-order traversal on a binary search tree produces the keys in sorted order, which is why it is the go-to for printing or validating a BST and for finding an in-order successor during deletion. Pre-order is the natural choice for copying or serializing a tree, since the root is emitted before its children and can be rebuilt first. Post-order visits children before their parent, which is exactly what you want when freeing memory, deleting a tree, or computing values that depend on subtree results (like height or expression evaluation). You should also be comfortable with both the recursive version, which is short and mirrors the definition, and the iterative version, which makes the hidden call stack explicit.

As you watch, keep a small sample tree on paper and trace along with the speaker rather than just listening. Pay attention to the moment a node is actually "visited" (printed) versus merely passed through on the way down, since that single detail is what separates the three strategies. For the iterative videos, watch what gets pushed onto the stack and when, and ask yourself how that sequence reproduces the recursive behavior.

Implementing a BST in JavaScript

Introduction

So far you have reasoned about binary search trees on paper — drawing nodes, following edges, and tracing where a value belongs. This topic turns that reasoning into working code. You will define a Node class that stores a value plus left and right references, wrap it in a BinarySearchTree class that tracks the root, and then add methods one at a time: insert, search (lookup), the three traversals, and finally delete with its three cases.

This matters because the code forces you to be precise in ways a diagram does not. Where does a new node actually get attached? What does your method return when the tree is empty, or when the key is not found? How do you reconnect a subtree after removing a node with two children? Writing the implementation yourself is the fastest way to discover which parts of the concept you only half understood.

The videos below are from a Java-based DSA series, and that is deliberate: the class structure, the recursive insert, and the recursive search translate almost line for line into JavaScript. While watching, focus on the shape of the logic rather than the syntax — the base case of each recursion, the comparison that chooses left versus right, and the fact that each recursive call returns a subtree reference that the parent must reassign.
