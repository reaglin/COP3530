Introduction

Before you can traverse, search, or rebalance a tree, you need a precise vocabulary for its parts. A binary tree is built from nodes, and each node is a small, self-contained unit: a field holding the data (often called the key or value) and two reference fields pointing to a left child and a right child. When either reference is null, that side of the node is empty — and a node with two null references is a leaf. Everything else about tree structure follows from how these nodes are linked together.

From those links come the relationships and measurements you will use all semester. One node is designated the root (the only node with no parent); every other node has exactly one parent and up to two children. The depth of a node is the number of edges from the root down to it, the height of a node is the number of edges on the longest downward path to a leaf, and the height of the tree is the height of its root. Any node, taken together with everything beneath it, forms a subtree — which is why so many tree algorithms are naturally recursive. Nodes sharing the same depth form a level, and a tree is considered balanced when the left and right subtrees of every node have heights that differ by at most a small constant.

These ideas are not just terminology. Tree height directly determines how long a search or insertion takes, so the difference between a balanced tree and a degenerate, list-like tree is the difference between logarithmic and linear performance. As you watch the videos below, pay attention to three things: how height and depth are defined (some sources count edges, others count nodes, so note which convention is used), how a recursive height computation mirrors the subtree structure, and what makes the minimum and maximum possible heights of an n-node tree so far apart.
