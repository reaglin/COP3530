Introduction

Hashing a password is only the first step in protecting it. If two users choose the same password, a plain hash produces the same output for both, and attackers can precompute enormous tables of hashes for common passwords and look up stolen values almost instantly. Salting — adding a unique, random value to each password before hashing — breaks those precomputed attacks and forces an attacker to work on every account separately.

This topic builds on what you already know about hash functions and applies it to the practical problem of storing credentials. You will look at how salts are generated with a cryptographically secure random source and stored alongside the hash, how a related secret called a pepper differs from a salt, and how key stretching deliberately makes each hash computation slow. From there the topic moves to the algorithms built for this job: bcrypt, scrypt, and Argon2, each with tunable work factors (and, for scrypt and Argon2, memory cost) that let defenders raise the price of an offline cracking attempt.

While watching, keep three questions in mind. First, which specific attack does each defense stop — rainbow tables, dictionary attacks, or raw brute force? Second, what has to be stored in the database, and what must stay secret? Third, how do you choose parameters: what makes a work factor "high enough" without making legitimate logins unacceptably slow?
