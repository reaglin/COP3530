Introduction to Hashing Algorithms

Introduction

A hash function takes an input of any size — a password, a file, a sentence, a multi-gigabyte disk image — and produces a fixed-length output, often called a digest or hash value. The same input always produces the same output, but even a one-bit change to the input should produce a completely different-looking digest. That deterministic, one-way transformation is the foundation for everything else in this module: password storage, file integrity checks, HMACs, and digital signatures all rest on it.

In this course you will meet hashing from two directions. In data structures, hash functions map keys into buckets of a hash table, where speed and even distribution matter most and collisions are expected and handled. In security, cryptographic hash functions must additionally resist attacks: it should be infeasible to recover the input from the digest (preimage resistance) or to find two inputs with the same digest (collision resistance). Recognizing that these are related but different design goals — and that MD5 is still fine for a checksum but broken for signatures — is a key takeaway.

As you watch, keep a short list going: What makes hashing different from encryption? (Hint: there is no key and no way back.) What does the avalanche effect look like in a worked example? Which algorithms are named, and what output lengths do they produce? Where does the speaker mention integrity verification, and what exactly is being compared to what?

Cryptographic Hash Functions

Introduction

In earlier parts of this course you used hash functions to spread keys across buckets in a hash table. The goal there was speed and even distribution; if two keys occasionally collided, chaining or probing handled it. Cryptographic hash functions start from the same basic idea — map arbitrary input to a fixed-size digest — but add security requirements that general-purpose hashes never promise: it must be infeasible to recover an input from its digest (preimage resistance), infeasible to find two inputs with the same digest (collision resistance), and a one-bit change in the input should scramble roughly half the output bits (the avalanche effect).

These properties are what make a digest usable as a stand-in for data itself: in file integrity checks, digital signatures, message authentication codes, blockchain structures, and — with important caveats covered later in this module — password storage. They also explain why algorithm choice matters. MD5 still computes quickly and is still seen in legacy systems, but practical collision attacks have broken it for any security purpose; SHA-256, part of the SHA-2 family, remains the common default for integrity and signing work.

As you watch, keep two questions in your head. First, which security property is each example relying on — is the system protected because digests are hard to invert, or because collisions are hard to find? Second, notice how small an input change needs to be before the digest becomes unrecognizable; that visual demonstration of the avalanche effect is the fastest way to internalize why digests work as fingerprints.

Password Hashing Fundamentals

Introduction

Storing passwords sounds simple until you consider what happens when a database is stolen. If passwords sit in plain text, a single breach hands an attacker every account immediately — and because people reuse passwords, the damage spreads to other services. The natural fix, running each password through a cryptographic hash like MD5 or SHA-256, is better but still weak: those functions are designed to be fast, which is exactly what an attacker guessing billions of candidates per second wants. Precomputed rainbow tables make matters worse, since identical passwords produce identical digests.

This topic walks through the fixes that modern systems actually use. A unique, randomly generated salt per user makes precomputation useless and ensures two users with the same password get different stored values. Dedicated password hashing algorithms — bcrypt, scrypt, and Argon2 — add a deliberately tunable work factor (and in scrypt's and Argon2's case, memory cost) so that each guess is expensive for the attacker while still fast enough for a legitimate login. You will also see the login verification flow: the system retrieves the stored salt and parameters, recomputes the hash from the submitted password, and compares the results.

As you watch, keep a few questions in mind. What exactly gets stored in the users table, and why does the salt not need to be secret? Where does a pepper differ from a salt? How would you choose a work factor, and what should happen to it as hardware gets faster? Finally, notice how the attack methods described in the third video map back to the specific defenses introduced in the first two.

Salting and Advanced Password Protection Techniques

Introduction

Hashing a password is only the first step in protecting it. If two users choose the same password, a plain hash produces the same output for both, and attackers can precompute enormous tables of hashes for common passwords and look up stolen values almost instantly. Salting — adding a unique, random value to each password before hashing — breaks those precomputed attacks and forces an attacker to work on every account separately.

This topic builds on what you already know about hash functions and applies it to the practical problem of storing credentials. You will look at how salts are generated with a cryptographically secure random source and stored alongside the hash, how a related secret called a pepper differs from a salt, and how key stretching deliberately makes each hash computation slow. From there the topic moves to the algorithms built for this job: bcrypt, scrypt, and Argon2, each with tunable work factors (and, for scrypt and Argon2, memory cost) that let defenders raise the price of an offline cracking attempt.

While watching, keep three questions in mind. First, which specific attack does each defense stop — rainbow tables, dictionary attacks, or raw brute force? Second, what has to be stored in the database, and what must stay secret? Third, how do you choose parameters: what makes a work factor "high enough" without making legitimate logins unacceptably slow?

Ensuring Data Integrity with Hashing

Introduction

Hashing is not only for storing passwords. Because a cryptographic hash produces a short, fixed-size fingerprint that changes drastically when even one bit of input changes, hashes are the standard tool for answering the question "is this data exactly what it was supposed to be?" In this topic you will see that idea applied to downloaded files, messages in transit, and software distributed by vendors.

The key distinction to keep in mind is what each mechanism actually proves. A plain checksum or file hash detects accidental corruption and, if the published hash comes from a trustworthy source, lets you spot a tampered download. An HMAC adds a shared secret key, so only someone holding that key can produce or verify the tag — this gives integrity plus authentication between two parties. A digital signature uses a private key to sign a hash of the message, so anyone with the corresponding public key can verify both integrity and origin, and the signer cannot credibly deny having signed it.

As you watch, look for three things: where the hash function sits in each workflow (what exactly is being hashed), what secret or key material is involved, and what threat each mechanism does and does not defend against. Those three questions are the backbone of the comparison you will be asked to make between checksums, HMACs, and digital signatures.

Common Attacks and Vulnerabilities

Introduction

Hashing is only as strong as the way it is used. A hash function that looks secure on paper can fail badly in practice when passwords are short, salts are missing, the algorithm is outdated, or the comparison code leaks information about how long it took to run. This topic surveys the attacks that exploit those weaknesses: brute-force and dictionary/wordlist guessing, precomputed rainbow tables, collision attacks against deprecated functions like MD5 and SHA-1, the consequences of unsalted hashing, and timing attacks on hash comparison.

In COP3530 you already think about cost in terms of time and space. These attacks are the security version of that same reasoning: an attacker is choosing between spending computation (guess every candidate) and spending storage (precompute a huge table of hashes), and defenses like salting, peppering, and key stretching exist to push that cost beyond what is practical. Understanding the tradeoff is what lets you argue why bcrypt, scrypt, or Argon2 belong in an authentication system instead of a bare call to SHA-256.

As you watch, keep a running list in two columns: the attack, and the specific countermeasure that defeats it. Pay attention to why a salt kills rainbow tables but does little against a targeted brute-force attack, why collision resistance matters for signatures and integrity checks more than for password storage, and why the birthday problem means collision resistance is roughly half the bit length of the digest.

Best Practices and Real-World Applications

Introduction

Everything you have learned about hash functions in this module comes together here: how practitioners actually choose and deploy hashing in production systems. Choosing "the right hash for the job" is not one decision but several — a fast general-purpose digest like SHA-256 is appropriate for file integrity and digital signatures, while password storage calls for a deliberately slow, memory-hard algorithm such as bcrypt, scrypt, or Argon2 with per-user salts and a tuned work factor. The same primitive also appears in message authentication (HMAC), in TLS handshakes and certificates, in blockchain block linking and Merkle trees, and in digital forensics where a hash value serves as a tamper-evident fingerprint of seized evidence.

This matters in COP3530 because hashing is where a data structures concept meets real security consequences. A hash table and a password database use the same underlying idea, but the engineering requirements are opposite: one wants speed, the other wants slowness and unpredictability. Understanding that distinction — and the surrounding practices of salting, peppering, key stretching, standards compliance, and periodic re-evaluation as hardware improves — is what separates a working implementation from a safe one.

As you watch the videos below, keep three questions in mind. First, what property of the hash function is each application relying on (preimage resistance, collision resistance, the avalanche effect, or just speed)? Second, what attack is each countermeasure defending against — a salt stops rainbow tables, a pepper defends against a database-only leak, a work factor slows brute force. Third, where does the secret live in each scheme: in nothing (a plain digest), in a stored server-side value (a pepper), in a shared key (HMAC), or in a private key (digital signatures).
