Introduction

Storing passwords sounds simple until you consider what happens when a database is stolen. If passwords sit in plain text, a single breach hands an attacker every account immediately — and because people reuse passwords, the damage spreads to other services. The natural fix, running each password through a cryptographic hash like MD5 or SHA-256, is better but still weak: those functions are designed to be fast, which is exactly what an attacker guessing billions of candidates per second wants. Precomputed rainbow tables make matters worse, since identical passwords produce identical digests.

This topic walks through the fixes that modern systems actually use. A unique, randomly generated salt per user makes precomputation useless and ensures two users with the same password get different stored values. Dedicated password hashing algorithms — bcrypt, scrypt, and Argon2 — add a deliberately tunable work factor (and in scrypt's and Argon2's case, memory cost) so that each guess is expensive for the attacker while still fast enough for a legitimate login. You will also see the login verification flow: the system retrieves the stored salt and parameters, recomputes the hash from the submitted password, and compares the results.

As you watch, keep a few questions in mind. What exactly gets stored in the users table, and why does the salt not need to be secret? Where does a pepper differ from a salt? How would you choose a work factor, and what should happen to it as hardware gets faster? Finally, notice how the attack methods described in the third video map back to the specific defenses introduced in the first two.
