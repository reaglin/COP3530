Introduction

Every time your program calls a function, the runtime has to remember where it was, what the local variables held, and where to send the return value. It does this with the call stack: a last-in, first-out structure of stack frames, one frame per active call. Recursion is where this bookkeeping becomes visible, because a single recursive function can have dozens or thousands of frames alive at once, each holding its own copy of the parameters and local state.

This topic matters in COP3530 because you cannot reason about recursive correctness or cost without a mental model of the stack. Tracing how frames are pushed on the way down to the base case and popped on the way back up is the same skill you will use later for tree traversals, divide-and-conquer sorting, and graph search. It is also where recursion fails: too much depth means stack overflow, and knowing why that happens tells you how to avoid it (a reachable base case, shallower recursion, memoization, or an iterative rewrite).

As you watch, keep a pen handy and draw the stack yourself. Look specifically for: what information a single frame stores, the exact moment the base case stops new frames from being created, the order in which frames resolve, and how the maximum depth relates to the input size. If a video uses Python or pseudocode rather than JavaScript, focus on the stack behavior — the mechanism is the same across languages.
