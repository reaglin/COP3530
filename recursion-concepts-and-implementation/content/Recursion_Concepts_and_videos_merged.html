What is Recursion?

Introduction

Recursion is a problem-solving strategy in which a function solves a problem by calling itself on a smaller version of that same problem. Instead of writing an explicit loop that repeats work, you describe the problem in terms of itself: a factorial of n is n times the factorial of n-1; the length of a list is one plus the length of the rest of the list. This self-referential way of thinking takes practice, which is why this topic focuses on the concept before we move into stack frames, tracing, and performance.

In COP3530, recursion matters because so many data structures are themselves recursive. A linked list is a node followed by another list; a tree is a node with subtrees. Once you are comfortable with recursive thinking, traversals, searches, and divide-and-conquer algorithms become much easier to express and reason about. Recursion is also the natural lead-in to understanding the call stack, which you will need for debugging and for recognizing why stack overflow happens.

As you watch these videos, look for three things. First, the two required pieces of any recursive function: a base case that stops the recursion and a recursive case that moves toward that base case. Second, how each presenter compares a recursive solution to an equivalent iterative one, and what they say about readability versus performance. Third, the vocabulary you will reuse all module long — base case, recursive call, stack, and divide and conquer.

Base Cases and Recursive Cases

Introduction

Every recursive function is built from two parts. The base case is the condition under which the function stops calling itself and simply returns a value; the recursive case is the branch in which the function calls itself on a smaller or simpler version of the original problem. Think of the recursive case as the engine that drives the computation forward and the base case as the brake that stops it at the right moment.

Both parts are required, and they must work together. A function with no reachable base case never stops, and each unfinished call keeps a stack frame alive until the runtime runs out of space and throws a stack overflow error. Just as dangerous is a recursive case that does not actually converge — for example, calling the function again on the same input, or shrinking the input in a way that skips past the stopping condition. In this course you will see this pattern repeatedly in factorial, Fibonacci, list and tree traversal, and divide-and-conquer algorithms, so recognizing the two components quickly is a skill worth building now.

As you watch the videos below, do three things. First, pause at each code example and point to the exact line that is the base case and the exact line that is the recursive case. Second, ask how the argument changes on each call and convince yourself it must eventually reach the base case. Third, notice how the speakers describe what happens on the call stack, since that is how an unterminated recursion turns into a crash rather than an infinite loop.

The Call Stack and Recursion

Introduction

Every time your program calls a function, the runtime has to remember where it was, what the local variables held, and where to send the return value. It does this with the call stack: a last-in, first-out structure of stack frames, one frame per active call. Recursion is where this bookkeeping becomes visible, because a single recursive function can have dozens or thousands of frames alive at once, each holding its own copy of the parameters and local state.

This topic matters in COP3530 because you cannot reason about recursive correctness or cost without a mental model of the stack. Tracing how frames are pushed on the way down to the base case and popped on the way back up is the same skill you will use later for tree traversals, divide-and-conquer sorting, and graph search. It is also where recursion fails: too much depth means stack overflow, and knowing why that happens tells you how to avoid it (a reachable base case, shallower recursion, memoization, or an iterative rewrite).

As you watch, keep a pen handy and draw the stack yourself. Look specifically for: what information a single frame stores, the exact moment the base case stops new frames from being created, the order in which frames resolve, and how the maximum depth relates to the input size. If a video uses Python or pseudocode rather than JavaScript, focus on the stack behavior — the mechanism is the same across languages.

Implementing Factorial with Recursion

Introduction

Factorial is the traditional first recursive function for a reason: its mathematical definition is already recursive. We write n! = n * (n-1)! for n > 1, and we declare 1! = 1 (and 0! = 1) as the stopping point. That definition hands you both pieces of a recursive function — a base case that returns an answer directly, and a recursive case that reduces the problem to a smaller version of itself.

In this topic you will translate that definition into JavaScript line by line: check for the base case first, then return n * factorial(n - 1). You will then trace factorial(4) by hand, watching stack frames pile up as each call waits on the one below it, and watching the multiplications resolve on the way back out. This tracing habit is the single most valuable skill in the module — it is how you will later reason about Fibonacci, list traversal, and stack overflow risk.

The videos below use Python rather than JavaScript. That is intentional: recursion is a control-flow idea, not a language feature, and the base case / recursive call / call stack structure is identical. As you watch, focus on where the base case is tested, what the recursive call returns, and how the presenter describes the calls unwinding. Then rewrite each example in JavaScript yourself — the syntax change is small, and doing the translation is good practice for MO2.

Fibonacci Sequence Using Recursion

Introduction

The Fibonacci sequence is defined by a simple rule: each number is the sum of the two before it, starting from 0 and 1. That definition is itself recursive, which makes Fibonacci the classic example of a function whose recursive case contains two recursive calls instead of one. In this topic you will write fibonacci(n) in JavaScript, decide which values must be handled as base cases (typically n equal to 0 and n equal to 1), and confirm that every path through the function eventually reaches one of them.

What makes Fibonacci more interesting than factorial is what happens to the call stack. Because each call spawns two more calls, the execution forms a branching tree rather than a single chain, and the same subproblems get recomputed over and over. Tracing fibonacci(4) or fibonacci(5) by hand on paper is the fastest way to see this: you will notice fib(2) appearing several times in the tree. That redundancy is why the naive version grows roughly exponentially in running time, even though it is only a few lines of code.

The videos below approach Fibonacci from the dynamic programming side, which is exactly where this conversation leads. As you watch, pay attention to how the presenter describes the repeated subproblems in the recursion tree, how memoization (the top-down approach) stores results so each value is computed only once, and how the bottom-up approach replaces recursion with a loop entirely. The code shown is not JavaScript, but the recursive structure, base cases and stack behavior translate directly; focus on the logic and then re-express it in JavaScript yourself.

Recursive List Traversal

Introduction

Recursive list traversal is the idea that a list — whether a JavaScript array or a linked list — can be processed by handling one element and then handing the rest of the structure to the same function again. Instead of writing a loop with an index counter, you define the problem in terms of itself: the first element plus the result of traversing everything after it. The base case is what stops the process, usually an empty list (or an index that has run past the end, or a null node), and it is what keeps the recursion from running forever.

This matters in COP3530 because lists are the structures you will work with constantly, and many of the data structures later in the course — linked lists, trees, graphs — are defined recursively. Once you can see a list as "a head plus a smaller list," recursive solutions for summing, searching, counting, printing, and transforming elements all follow the same shape. You will also see clearly how each call adds a stack frame, which connects list traversal back to the call stack discussion and to the practical limits of recursion on large inputs.

As you watch, pay attention to three things: exactly how each author states the base case, how the "rest of the list" is produced (a slice, an incremented index, or a next pointer), and where the work on the current element happens — before the recursive call or after it returns. Also try to mentally compare each recursive version with the loop you would have written instead, so you can judge which is clearer and which is cheaper.

When to Use Recursion

Introduction

Recursion is not just a clever trick — it is a design choice. Almost any recursive routine can be rewritten as a loop, and almost any loop can be rewritten recursively, so the real question in this topic is not "can I?" but "should I?" You will compare the two approaches along several axes: how naturally each one maps to the structure of the problem, how readable the resulting code is, and what each costs in time and memory once the call stack gets involved.

Some problems are self-similar by nature. Trees, nested lists, divide-and-conquer sorting, graph and directory traversal, and backtracking searches all break down into smaller copies of themselves, and recursive code for them is often shorter and closer to the definition of the problem. Simple linear repetition — summing an array, counting to n, scanning a list — usually reads more clearly and runs faster as a loop. Learning to spot which category a problem falls into is the practical skill this topic is building.

As you watch, keep two questions in mind. First, what is the shape of the problem the speaker is solving — is it linear, or does it branch? Second, what is the hidden cost — how many stack frames pile up, and are any subproblems being recomputed? Note especially the naive Fibonacci example, which appears repeatedly in this course as the standard illustration of how an elegant recursive definition can become an exponentially expensive program.
