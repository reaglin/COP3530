Introduction to Graph Data Structures

Introduction

A graph is a data structure made of vertices (also called nodes) connected by edges. Unlike arrays, lists, or trees, graphs place no restriction on how items may connect: any vertex can link to any number of others, connections can be one-way or two-way, and cycles are allowed. That flexibility is exactly why graphs model so many real systems — road networks, social connections, web links, course prerequisites, and dependency chains in software.

In this course, graphs are the structure that ties together much of what you have already learned. Before you can implement adjacency lists or trace BFS and DFS, you need a precise vocabulary: vertex, edge, directed versus undirected, weighted versus unweighted, adjacency, degree, path, cycle, and connected versus disconnected. Getting these terms right early makes the later material about representation and traversal far easier to follow, because every algorithm description assumes them.

As you watch, focus on three things. First, how each video draws a graph and names its parts, so you can read a diagram quickly. Second, the difference an arrow makes — what changes when an edge is directed. Third, the terminology around moving through a graph (walks, paths, cycles), since traversal algorithms are formally described in those terms. Try sketching a small graph of your own, such as five friends and who follows whom, and label it using the vocabulary from each video.

Directed and Undirected Graphs

Introduction

A graph is one of the most flexible data structures you will meet in this course: it is simply a set of vertices (nodes) plus a set of edges that connect pairs of them. That minimal definition is powerful because almost any relationship can be modeled with it — friendships, road networks, web links, course prerequisites, package dependencies, and task scheduling. Before you can store a graph or traverse it, you need to be fluent in the vocabulary (vertex, edge, degree, path, cycle, adjacency) and in the single most important modeling decision: whether the edges have direction.

In an undirected graph, an edge between A and B means the relationship runs both ways — if A is a Facebook friend of B, then B is a friend of A. In a directed graph (digraph), each edge points from a source to a target, so A following B on Twitter says nothing about B following A. That distinction changes how you count degree (in-degree and out-degree instead of a single degree), how you store the graph (one entry or two in an adjacency list), and what questions you can ask (reachability, cycles, topological order).

As you watch these videos, keep a running list of two things. First, the terminology: write down each term and a one-sentence definition in your own words, because the rest of the module assumes it. Second, the direction question: for every example shown, ask yourself whether the relationship is inherently symmetric (undirected) or asymmetric (directed), and how the answer would change the code you write later in the module.

Adjacency Matrix Representation

Introduction

A graph is just a set of vertices and the edges that connect them, but before you can write code that works on a graph you have to decide how to store it. The adjacency matrix is the most direct answer: number the vertices 0 through n-1, then build an n-by-n table where the entry in row i and column j records whether an edge runs from vertex i to vertex j. For an unweighted graph the entries are typically 1 and 0; for a weighted graph they can hold the edge weight instead.

This representation matters in COP3530 because it is one half of the central design trade-off you will be asked to reason about all module long. A matrix always occupies space proportional to the square of the vertex count, regardless of how few edges exist, but it answers the question "is there an edge between u and v?" in constant time. The adjacency list flips both of those properties. Knowing which one to reach for depends on whether your graph is dense or sparse, and on which operations your algorithm performs most often.

As you watch, pay attention to a few specific things. First, notice how symmetry across the main diagonal signals an undirected graph, and how a directed graph's matrix is generally asymmetric. Second, track the complexity claims carefully: space, edge lookup, adding or removing an edge, and iterating over all neighbors of a vertex are each different costs. Third, watch for how the presenters handle weighted edges and self-loops, since those details often show up in assignments.

Adjacency List Representation

Introduction

A graph is just a set of vertices and the edges that connect them, but before you can run any algorithm on one, you have to decide how to store it in memory. The adjacency list is the representation you will use most often in this course: for every vertex, you keep a list (or array, or set) of the vertices it connects to. In JavaScript this usually looks like an object or a Map whose keys are vertex labels and whose values are arrays of neighbors.

The reason this representation matters is efficiency. An adjacency matrix stores a cell for every possible pair of vertices, which costs O(V^2) space no matter how few edges exist; an adjacency list costs roughly O(V + E), which is a huge win for sparse graphs such as road networks, social graphs, or dependency graphs. The trade-off is that checking "is there an edge from u to v?" requires scanning u's list instead of a single constant-time lookup, so neither representation is universally better.

As you watch, pay attention to three things. First, how the structure changes between directed and undirected graphs: in an undirected graph each edge appears twice, once in each endpoint's list. Second, how the authors count space and time, and which operations favor the list versus the matrix. Third, the mechanics of actually building the structure in code, so you can translate the Java or pseudocode you see into the JavaScript Graph class you will write later in this module.

Breadth-First Search (BFS)

Introduction

Breadth-First Search (BFS) is a graph traversal strategy that explores a graph in layers: starting from a source vertex, it visits every neighbor at distance one, then every vertex at distance two, and so on. The engine behind this level-by-level behavior is the queue, a first-in-first-out structure that holds vertices waiting to be explored. Alongside the queue you also need a visited set (or boolean array) so that cycles and shared neighbors do not cause a vertex to be processed twice.

BFS matters in this course because it is one of the two canonical traversals you will implement on top of your adjacency list representation, and because its level order gives it properties DFS does not have — most notably, in an unweighted graph BFS finds the shortest path in number of edges from the source. It also forces you to think about graphs that are not fully connected: a single BFS call only reaches the component containing the start vertex, so a complete traversal requires looping over all vertices and launching a new BFS from each unvisited one.

As you watch the videos below, focus on four things: exactly when a vertex is marked visited (on enqueue, not on dequeue, if you want to avoid duplicates), how the queue contents change at each step, how the traversal order depends on the order neighbors appear in the adjacency list, and where BFS shows up in practice — shortest paths, level/distance computation, web crawling, social network degrees of separation. Try tracing a small graph by hand before and after watching, and compare your order against the one in the video.

Depth-First Search (DFS)

Introduction

Depth-First Search (DFS) is one of the two fundamental ways to systematically visit every vertex in a graph. The strategy is simple to state: from the current vertex, follow one edge as deep as you can, and only when you run out of unvisited neighbors do you back up (backtrack) and try another branch. That "go deep first" behavior is what separates DFS from BFS, which fans out level by level.

In this course, DFS matters for two reasons. First, it is a building block: cycle detection, topological sorting, finding connected components, path existence checks, and maze/puzzle solving are all DFS in disguise. Second, it is a good test of your understanding of recursion and explicit stacks — the recursive version hides the stack in the call stack, while the iterative version makes that stack visible, and the two can produce different (but equally valid) visit orders.

As you watch, keep a short checklist in mind: Where is the visited set maintained, and when is a vertex marked visited (on push, or on pop)? How is backtracking actually happening? What happens if the graph is disconnected — how does the algorithm restart from an unvisited vertex? And how would the same pseudocode map onto an adjacency list in your own Graph class? Try tracing each example by hand on paper before the video reveals the answer.

Implementing Graph Traversal in JavaScript

Introduction

So far in this module you have studied graphs on paper: vertices, edges, directed versus undirected relationships, and the trade-offs between adjacency matrices and adjacency lists. Now you will turn those ideas into working code. The goal of this topic is to build a reusable Graph class in JavaScript that stores its edges as an adjacency list (commonly a Map or object whose keys are vertices and whose values are arrays of neighbors), exposes a method for adding edges, and then supports traversal.

Traversal is where the structure earns its keep. Breadth-first search uses a queue and a visited set to explore a graph level by level, while depth-first search follows one path as far as it can before backtracking. DFS can be written two ways: recursively, where the JavaScript call stack does the bookkeeping for you, or iteratively, where you manage an explicit stack. Writing both versions makes the relationship between recursion and stacks concrete, and it prepares you to handle graphs large enough that deep recursion becomes risky.

The videos below walk through implementations of BFS, recursive DFS, and iterative DFS on an undirected graph. While watching, pay attention to three things: how the graph is represented and how edges get added for an undirected graph (both directions), where the visited set is checked and updated, and the exact order in which vertices are printed. Afterward, run the same graph through all three traversals yourself and compare the output orders so you can explain why they differ.
