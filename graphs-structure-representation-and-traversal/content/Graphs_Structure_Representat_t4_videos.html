Introduction

A graph is just a set of vertices and the edges that connect them, but before you can run any algorithm on one, you have to decide how to store it in memory. The adjacency list is the representation you will use most often in this course: for every vertex, you keep a list (or array, or set) of the vertices it connects to. In JavaScript this usually looks like an object or a Map whose keys are vertex labels and whose values are arrays of neighbors.

The reason this representation matters is efficiency. An adjacency matrix stores a cell for every possible pair of vertices, which costs O(V^2) space no matter how few edges exist; an adjacency list costs roughly O(V + E), which is a huge win for sparse graphs such as road networks, social graphs, or dependency graphs. The trade-off is that checking "is there an edge from u to v?" requires scanning u's list instead of a single constant-time lookup, so neither representation is universally better.

As you watch, pay attention to three things. First, how the structure changes between directed and undirected graphs: in an undirected graph each edge appears twice, once in each endpoint's list. Second, how the authors count space and time, and which operations favor the list versus the matrix. Third, the mechanics of actually building the structure in code, so you can translate the Java or pseudocode you see into the JavaScript Graph class you will write later in this module.
