Introduction to Lists and Arrays

Introduction

Data structures are the organized ways we store data in memory so that a program can find it, change it, and reuse it efficiently. Arrays and lists are the two starting points for almost every other structure you will meet in this course: an array is a fixed-size block of contiguous memory whose elements are reached by index, while a linked list is a chain of nodes where each node holds a value and a reference to the next node. Both are ordered collections, but they organize memory in very different ways, and that difference drives everything else.

This topic matters because the rest of COP3530 builds on it. Stacks, queues, hash tables, trees, and graphs are all implemented on top of array-like or node-based storage, and the trade-offs you learn here — fast indexed access versus cheap insertion and deletion — reappear constantly. Getting comfortable now with how memory is laid out, what indexing really means, and when resizing is required will make the Big O analysis later in the module feel like a natural next step rather than a separate subject.

As you watch, keep a short comparison table going. For each structure, note: how elements are located (by index or by following links), whether the size is fixed or grows, what happens when you insert or delete at the front, middle, or end, and what extra memory the structure costs. Try to express each answer in plain words first; attaching Big O labels comes later in the module.

Array Structure and Memory Layout

Introduction

An array is the simplest and most fundamental data structure you will study in this course: a fixed-size block of memory holding elements of the same type, laid out one after another with no gaps. Because the elements are contiguous, the computer does not need to search for an element — it can compute exactly where element i lives using the address of the first element, the index, and the size of each element. That single idea, direct address calculation, is why array access is constant time and why arrays serve as the building block for so many other structures.

The details matter. Zero-based indexing is not an arbitrary convention; it falls out of the address formula, since the first element sits zero elements away from the base address. Fixed size and static allocation matter too: when an array is declared, the space is reserved up front, so growing it later usually means allocating a new, larger block and copying. And accessing an element by index is a completely different operation from searching for a value — one is a calculation, the other requires examining elements until you find a match.

As you watch, pay attention to three things: how the memory address of an element is computed, where in memory arrays actually live (stack versus heap, and who hands out that memory), and the distinction between knowing an index and having to look for a value. Keep a mental note of how these mechanics will later explain the Big O costs you will assign to array operations.

List Structure and Dynamic Behavior

Introduction

An array gives you a fixed block of memory: you decide how many slots you need, and that decision is locked in when the array is created. A list, by contrast, is designed to be dynamic — it grows and shrinks as elements are added and removed, so the programmer does not have to predict the final size in advance. This topic examines how that dynamic behavior is actually achieved, either by reallocating and copying a larger backing array behind the scenes, or by linking separately allocated nodes together so that each new element simply gets its own piece of memory.

These mechanics matter for the rest of the course because they explain where the cost of an operation comes from. Resizing an array is not free: a new, larger block must be allocated and every existing element copied into it. Linked structures avoid that copying but give up the constant-time indexed access that contiguous memory provides. Understanding both mechanisms is what lets you say, with evidence, why one structure is the better fit for a given use case.

As you watch, pay attention to three things: what happens in memory at the moment a structure runs out of room, how elements are shifted or re-linked when something is inserted or removed in the middle, and how you reach the element at a particular position. Keep a running list of the trade-offs you notice — fixed versus variable size, contiguous versus scattered memory, cheap indexing versus cheap insertion. Those notes will feed directly into the Big O discussion later in this module.

Core Data Operations on Lists and Arrays

Introduction

Every data structure, no matter how simple or complex, is ultimately judged by what you can do with it and how much that costs. For lists and arrays, four operations form the core vocabulary: accessing an element at a given position, searching for an element by value, inserting a new element, and deleting an existing one. This topic asks you to describe each of these precisely — what steps the machine actually performs — before attaching any complexity notation to them.

The critical insight in this topic is that cost depends on position. Accessing the fifth element of an array is not the same work as accessing the fifth element of a singly linked list; inserting at the front of an array is not the same work as inserting at the end. Once you can articulate why shifting elements, traversing pointers, or indexing directly differ in effort, Big O notation becomes a natural shorthand rather than a memorized table.

The videos below extend the same operation vocabulary to other structures. As you watch, keep a running mental checklist: for each operation shown, ask where the work happens, whether the position of the operation changes the amount of work, and how the structure's layout makes some operations cheap and others expensive. That habit of questioning — not the specific structures demonstrated — is what carries into the rest of the course.

Introduction to Computational Complexity

Introduction

Computational complexity is the study of how the cost of running an algorithm grows as the amount of data it handles grows. Instead of timing code with a stopwatch — which depends on your machine, your language, and what else your computer is doing — we count the operations an algorithm performs as a function of the input size, usually called n. This gives us a machine-independent way to compare two approaches before we ever write them.

This matters in COP3530 because almost every decision you make about data structures is really a decision about cost. Reading the tenth item of an array, searching an unsorted list, or inserting at the front of a structure all have different costs, and those differences only become visible when n is large. Complexity analysis is the vocabulary you will use for the rest of the course to justify why one structure beats another for a given job.

As you watch, pay attention to four things: how each presenter identifies the input size, which operations they decide to count, how they distinguish best, average, and worst cases, and why they throw away constants and lower-order terms. That last habit — abstraction — can feel like cheating at first, but it is what lets us say something true about an algorithm's behavior at any scale rather than a single measurement on one computer.

Big O Notation Fundamentals

Introduction

Big O notation is the standard vocabulary computer scientists use to describe how the cost of an algorithm grows as the size of its input grows. Instead of measuring runtime in seconds — which depends on your machine, your compiler, and what else is running — Big O describes the shape of the growth curve: does the work stay flat as data grows (O(1)), grow in step with the data (O(n)), or explode as the data grows (O(n^2))?

In this module, Big O is the tool that lets you compare arrays and lists honestly. Accessing an element by index in an array is a constant-time operation; searching an unsorted list means potentially touching every element; nested loops over the same collection produce quadratic behavior. Once you can label these patterns, you can justify choosing one structure over another instead of guessing.

As you watch, focus on three habits. First, learn to count operations in terms of n rather than in absolute numbers. Second, practice dropping constants and non-dominant terms — why 3n + 50 is simply O(n), and why n^2 + n collapses to O(n^2). Third, build intuition for the relative ordering of complexity classes so that, when you later analyze insertion or deletion at the front versus the back of a structure, the Big O label comes naturally.

Applying Big O to List and Array Operations

Introduction

Big O notation becomes genuinely useful the moment you apply it to real operations on real structures. In this topic you take the four core operations you already know — access, search, insertion, and deletion — and attach a cost class to each one as it behaves on an array and on a linked list. Accessing an array element by index is O(1) because address arithmetic finds the slot directly, while searching an unsorted sequence is O(n) because, in the worst case, every element must be examined. Insertion and deletion are the interesting cases: the cost depends on position, since shifting elements in an array or walking to a node in a list changes the work required.

This matters because data structure selection is an engineering decision, not a style preference. Once you can say that an array gives O(1) indexed access but O(n) insertion at the front, and that a linked list reverses that profile, you can justify a choice for a specific use case rather than guessing. That reasoning — matching the operations your program performs most often to the structure that makes them cheap — is the skill the rest of COP3530 builds on.

As you watch, focus on the counting method: how does the presenter decide which statements execute once versus n times, and how do constants and lower-order terms get dropped? Pay attention to the vocabulary of complexity classes so you can recognize O(1), O(n), and O(n^2) patterns on sight, and keep asking yourself which array or list operation each example resembles.
